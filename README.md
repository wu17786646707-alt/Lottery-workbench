# 双彩研究工作台 V17.0｜实盘形态审计 + 同预算复式对照 + 数据延迟修复

本版本基于 V16 完整兼容更新，适合以 iPhone 维护 GitHub Pages。**先在本机测试；不自动购票，也不会提高既定预算。**

## 本次已完工

1. 新增 **复盘诊断 V17** 页面（导航栏中“研究战绩”之后）。每份 GitHub 赛前锁定记录如已有真实目标期开奖，可核查 A/B/C/随机基准的命中、龙头、凤尾、三区比例误差、和值、跨度、软杀号误伤等。旧版本没有赛前保存的特征标注为“未预先记录”，不事后冒充预测。若手机已收录开奖结果但公开档案尚未结算，明确显示“本机临时核对”，不把本地计算当作仓库结算。
2. 同成本的 **两种复式结构**：双色球 8+1 与 7+4 都是 28 注、56 元；大乐透 7+2 与 5+7 都是 21 注、42 元。比较只用于研究，不同时默认选择两组；替代方案包含该研究员的原单式。两种同注数方案中一等奖的数学概率相同。
3. 官方开奖前自动记录仍由 A、B、C 和随机基准构成。V17 新建记录的软杀号、形态、选球说明按当时算法和历史基准保存。到目标期开奖且真数据存在后，自动追加 `audit` 复盘和首次结算时间；旧锁定号码不修改。
4. 修复 V16 软杀号 **计算时被乘以 0 而实际没有降权** 的问题：使用微小的评分惩罚，仍不硬排除号码。这是研究上的新假设，不是开奖概率提升证据。
5. 修复本机 A/B/C 缓存判定写死旧策略版本的问题，避免无意义地重复重建候选。
6. 更新 `sync_history.py`：对 GitHub raw 与 GitHub API 读取的**同一上游数据库**比较最新有效期号，选更新的一份；如果失败再回退 CDN。它减少单一路径缓存滞后，但 **不是独立双源验证**。保留官方 API 403/567 提示，数据不符仍隔离。
7. 后台健康状态增加最近检查时间、日程滞后天数、首次观察到新期次的时间（不冒充官方公告时间）。
8. **可选**更新 GitHub Actions 现有工作流的调度频次，改成北京时间 21:26/22:26/23:26/00:26/01:26/02:26/07:16/10:16，依然是 GitHub 的尽力而为调度，不能保证秒级及时。

## 唯一重要的数学结论

双色球单注一等奖概率 = 1 / 17,721,088；大乐透单注 = 1 / 21,425,712。无论冷号、热号、形态、连号还是软杀号，对公平独立开奖没有已证实的单注概率提升。同彩种、同数量不重复注数的一等奖概率完全相同，复式增加组合覆盖也同比增加成本。拒绝暗示中奖保证。

## 数据和部署边界

- **不可覆盖**：仓库里的 `history.json`、`research.json`、`health.json`、`official_latest.json`、`icon.svg`、`package.json` 和既有工作流文件（除非按照“可选增强”明确编辑）。
- 旧公开锁定记录、开奖与研究战绩原样保留；研究版本仍按原先显示 V12/V13/V16，**仅未来新建记录**使用 `research-v17.0-shape-first`。
- 不修改 IndexedDB 键 `lottery_v12` / localStorage 的现有格式；切换前先做完整 JSON 备份。
- 附件中 **01_上传这17个文件到仓库根目录** 的 17 个文件一次性上传。不需要删除任何旧文件、不需要云服务器。
- 完整部署只需这一份 ZIP；第 02 项 GitHub Actions 调度增频属于**可选的第二次编辑**，不做也能使用新版复盘及采集线路优化。

## iPhone 验收重点

1. GitHub Pages 首页顶部版本 `V17.0`；两个彩种原有选号和 V16 形态页面正常。
2. 打开 `复盘诊断 V17`：选旧记录看到真实已结算/临时核对、形态误差与“未预先记录”；不会凭空把旧杀号规则补算成赛前成绩。
3. 双色球同预算比较 `8+1` 与 `7+4`，显示 **28 注 / 56 元**且概率相等；大乐透显示 `7+2` 与 `5+7`，**21 注 / 42 元**且概率相等。
4. 进入 `数据与备份`：历史期数与已有真实记录不减少；源异常继续有警示。
5. 去 Actions 手动 `Run workflow` 一次，检查 `health.json` 是否更新；若新的真实期开奖已经可由上游获取，`research.json` 中对应待结算记录应被核对；否则显示待结算，不会伪造。
